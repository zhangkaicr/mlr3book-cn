10.1 并行化（Parallelization）

术语「并行化」指的是并行运行多个算法，即在多个 CPU 核心、CPU 或计算节点上同时执行它们。并非所有算法都能并行化，但当它们可以时，并行化能显著节省计算时间。

一般而言，根据执行计算所用的硬件，有许多并行化的可能性。如果你只有带多个核心的单颗 CPU，那么线程（threads）或进程（processes）是利用本地机器所有核心的方式。另一方面，如果你有多台机器，它们可以通过网络套接字（network sockets）或消息传递接口（Message Passing Interface）等协议进行通信和交换信息。较大的计算站点依赖调度系统（scheduling systems）为多个用户编排计算，并且通常提供一个所有机器都能访问的共享网络文件系统。在计算集群上与调度系统交互的内容在第 11.2 节中借助 R 包 batchtools 介绍。

本节会用到一些与并行化相关的术语：

  • 并行化后端（parallelization backend）是指用于并行化的硬件，以及由某个 R 包提供的相应接口。许多并行化后端有不同的 API，因此我们使用 future 包作为许多并行化后端的统一抽象层。从用户的角度来看，mlr3 直接与 future 对接，所以你只需在开始任何计算前配置好后端即可。另外，mlr3 也为 mirai 包提供直接支持，它提供了一个每个任务开销更低、更轻量的后端（见第 10.1.6 节）。
  • 主进程（Main process）是编排计算工作（即任务 job）的 R 会话或进程。
  • 工作进程（Workers）是接收任务、执行计算然后把结果发回主进程的 R 会话、进程或机器。
并行化后端（Parallelization Backend）

并行编程中的一个重要步骤是识别程序流程中既耗时（「瓶颈」）又能与另一段程序独立运行的部分，即 A 段的操作不依赖于 B 段的结果，反之亦然。幸运的是，对于机器学习实验来说，这些部分通常比较容易发现：

  1. 训练学习算法（或机器学习流水线中其他计算密集的部分）可能包含可以并行运行的独立片段，例如
    • 单棵决策树会遍历所有特征以寻找最佳分裂点，每个特征的处理相互独立。
    • 随机森林通常会独立拟合数百棵树。
    让这些例子（以及统计与机器学习中许多领域普遍如此）可以并行化的关键原则被称为数据并行（data parallelism），意思是同一个操作被并发地施加到输入数据的不同元素上。学习算法的并行化在第 10.1.1 节中介绍。
  2. 重采样由多次独立的训练-测试划分重复组成，而基准测试（benchmarking）由多个独立的重采样组成（第 10.1.2 节）。
  3. 调优（第 4 章）通常是迭代式的基准测试，它嵌入在一个顺序流程中，由该流程决定接下来要尝试哪些超参数配置。虽然许多调优算法在某种程度上本质上是顺序的，但也有些算法（例如随机搜索）可以并行地提出多个配置供独立评估，从而提供另一个并行化层次（第 10.1.4 节）。
  4. 单个学习器对多个观测的预测可以独立计算（第 10.1.5 节）。
数据并行（Data Parallelism）

这些例子被称为「令人尴尬的并行」（embarrassingly parallel），因为它们非常容易并行化。如果我们能把问题表述成一个可以传给 map 类函数（如 lapply()）的函数，那这就是一个令人尴尬的并行问题。然而，一个问题能够被并行化，并不意味着问题中的每个操作都应该被并行化。启动和终止工作进程以及工作进程之间可能的通信都是有代价的，这个代价体现为额外需要的运行时间，被称为并行化开销（parallelization overhead）。这种开销在不同并行化后端之间差异很大，必须与顺序执行的运行时间仔细权衡，才能判断并行化是否值得。如果顺序执行已经相当快，启用并行化可能只会引入额外的复杂度而几乎不节省运行时间，甚至可能拖慢执行。我们可以控制并行化的粒度（granularity）来降低并行化开销。例如，我们可以把一个 10000 次迭代的 for-循环在两个 CPU 核心上并行化的开销，通过把 10000 个任务的工作分块（chunking）成两个各执行 5000 次迭代的计算任务来降低，结果得到两个大任务而非 10000 个小任务。

令人尴尬的并行（Embarrassingly Parallel）并行化开销（Parallelization Overhead）粒度（Granularity）

下面的代码块用 parallel 包的套接字集群（socket cluster）说明了这一效应，该包有 chunk.size 选项，因此我们无需手动创建分块：

# 在本地机器上设置一个含 2 个工作进程的套接字集群
library(parallel)
cores = 2
cl = makeCluster(cores)

# 要操作的向量
x = 1:10000

# 要并行化的快速函数
f = function(y) sqrt(y + 1)

# 不分块的方法：1000 个任务
system.time({parSapply(cl, x, f, chunk.size = 1)})
   user  system elapsed 
  0.761   0.543   1.579 
# 分块的方法：4 个任务
system.time({parSapply(cl, x, f, chunk.size = 5000)})
   user  system elapsed 
  0.005   0.000   0.062

只要你能通过设置分块大小来控制粒度，就应该至少让任务数不少于工作进程数。然而，如果任务分块太少且运行时间差异很大，系统最终可能一直等待最后一个分块完成，而其他资源处于空闲状态。这被称为同步开销（synchronization overhead）。因此，你应该争取让每个分块的运行时间至少有数秒，使并行化开销保持在合理范围，同时仍有足够多的分块来确保能充分利用系统。如果你的运行时间差异很大，可以考虑对任务进行分组，使各分块的运行时间更均匀。如果运行时间可以被估计，那么 batchtools::binpack() 和 batchtools::lpt()（与 chunk() 函数一同有文档）都可用于对任务分块。如果运行时间无法估计，那么对任务顺序做随机化会很有用。否则任务可能会碰巧按运行时间排序，例如因为它们按某个对训练时间影响很大的超参数排序。天真地对任务分块可能导致某些分块包含比其它分块昂贵得多的任务，从而造成可避免的资源利用不足。mlr3misc 自带了 chunk() 与 chunk_vector() 函数，它们可以方便地对任务分块，并且默认还会打乱任务顺序。在 mlr3 中也有一些控制并行化分块大小的选项，这些在第 10.1.2 节中讨论。

可重现性（Reproducibility）

并行化过程中可重现性往往令人担忧，因为可能需要特殊的伪随机数生成器（PRNG）(Bengtsson 2020)。然而，future 确保所有工作进程都会收到相同的 PRNG 流，与工作进程数量无关 (Bengtsson 2020)。因此，只要你在脚本开头使用 set.seed（并选用你偏好的 PRNG），mlr3 实验就是可重现的。

背景与解释（译者注）：理解「线程、进程、节点」这三层并行模型有助于把握本节内容：线程（thread）是进程内的轻量级执行单元，共享内存、启动开销极小，通常由底层 C/C++ 编译代码使用（例如 ranger 的 num.threads）；进程（process）是独立的内存空间，启动与通信开销较大（例如 future 的 multisession 后端）；而计算节点则是通过网络通信的独立机器。「数据并行」是指同一函数应用于不同数据切片，对应 R 中的 lapply() 一族；「令人尴尬的并行」指任务之间完全独立、无需通信，这是机器学习实验中最理想也最常见的并行模式。最后要提醒：并行化并非免费午餐，开销包括启动/销毁工作进程、序列化传输对象、同步等待等；当单个任务本身就很快时，并行反而更慢——这正是作者用 10000 次 sqrt() 演示「分块」收益的原因。

10.1.1 学习器的并行化（Parallelization of Learners）

在最底层，外部代码可以在底层实现支持并行时进行并行化。例如，在拟合单棵决策树时，每次把数据分成两个不相交子集的分裂都需要在全部 \(p\) 个特征上搜索最佳切分点。我们不必顺序遍历所有特征，而是可以把搜索拆分成 \(p\) 个线程，每个线程在单个特征上搜索最佳切分点。这些线程随后可以根据可用的 CPU 核心来调度，因为线程之间无需通信。所有线程完成后，结果被收集并合并，然后线程终止。每个特征的最优切分点共 \(p\) 个，通过顺序遍历这 \(p\) 个结果，把它们聚合成所有特征上的单一最优切分点。

GPU 计算（GPU Computation）

本书不涉及 GPU 上的并行化。mlr3 只分发多个学习器的拟合，例如在重采样、基准测试或调优期间。在这个相当抽象的层面上，GPU 并行化无法高效工作。然而，有些学习过程可以针对 CUDA/OpenCL 编译，从而在拟合单个模型时利用 GPU。请参考相应学习器实现的文档，例如 XGBoost 参见 https://xgboost.readthedocs.io/en/stable/gpu/。

线程化是在包的编译代码中实现的（例如 C 或 C++），这意味着 R 解释器调用外部代码并等待结果返回，而不会注意到计算是并行执行的。因此，线程化可能与某些并行后端冲突，最乐观的情况是系统被过度使用，最坏的情况是导致挂起或段错误（segfault）。出于这个原因，我们引入了「线程化并行默认关闭」的约定。控制线程数量的超参数被标记为 "threads" 标签：

lrn_ranger = lrn("classif.ranger")

# 显示所有带 "threads" 标签的超参数
lrn_ranger$param_set$ids(tags = "threads")
[1] "num.threads"
# 线程数初始化为 1
lrn_ranger$param_set$values$num.threads
[1] 1

要为此学习器启用并行化，mlr3 提供了辅助函数 set_threads()，它会自动调整与内置学习器并行化相关的超参数：

# 使用四个 CPU
set_threads(lrn_ranger, n = 4)

  • 你想同时把系统用于其他用途。
  • 你处于一个多用户系统上，想为其他用户留出一些资源。

为控制设置多少核心，我们建议在系统的 .Rprofile 文件中手动设置 CPU 数量：

options(mc.cores = 4)

还有其他学习器并行化的方法，例如直接支持某个特定的并行化后端，或支持像 foreach 这样的并行化框架。如果支持，必须显式激活并行化，例如通过设置一个超参数。如果你需要在学习器层面并行化，是因为单次模型拟合耗时太长，而你只拟合少数这类模型，请查阅相应学习器的文档。在许多场景下，在重采样或基准测试等更高层面并行化更有意义，这将在下面的小节中介绍。

背景与解释（译者注）：「线程」与「进程」在此的区别很关键：线程并行（如 ranger 的 num.threads、XGBoost 的 nthread）发生在 R 之外的编译代码里，R 解释器「感知不到」并行，因此如果同时又启用了 multisession 等进程级后端，就会出现过度订阅（oversubscription）——核心数被两边同时占用，甚至可能崩溃。所以 mlr3 的约定是：默认把线程数设为 1，由用户按需通过 set_threads() 打开。阿姆达尔定律说明加速比存在上限（\(1/((1-f)+f/N)\)，其中 f 为可并行比例、N 为核心数），这也是「不是核越多越快」的理论根源；而 availableCores() 只报告硬件有多少核，无法知道当下有多少核被其他进程占用，因此作者建议在 .Rprofile 中手动设定一个保守的核数。

10.1.2 重采样与基准测试的并行化（Parallelization of Resamplings and Benchmarks）

除了并行学习器之外，大多数机器学习实验在重采样期间都可以轻松并行化。根据定义，重采样是对多个独立训练-测试划分的重复进行聚合而执行的。

mlr3 利用 future 通过并行后端实现对重采样迭代的并行化，该后端可以由用户通过 plan() 函数配置。

举例来说，我们将考察在 sonar 任务上对决策树做三折交叉验证的并行化（图 10.1）。我们使用 multisession 计划（它内部使用 parallel 包的套接字集群），该计划在所有操作系统上都应该可用。

library(future)

# 选择要使用的 multisession 后端
future::plan("multisession")

# 运行我们的实验
tsk_sonar = tsk("sonar")
lrn_rpart = lrn("classif.rpart")
rsmp_cv3 = rsmp("cv", folds = 3)
system.time({resample(tsk_sonar, lrn_rpart, rsmp_cv3)})
   user  system elapsed 
  0.512   0.016   7.293

默认情况下，除非你在 future::plan() 中指定 workers 参数，否则会使用你机器的所有 CPU（参见上一节关于这可能引起的问题）。与线程相比，对于 "multisession" 后端而言，启动工作进程、通信传递对象、传回结果以及关闭工作进程的技术开销相当大。

multicore 后端的开销比线程化大，但比 "multisession" 小得多，因为 "multicore" 后端只在对象被修改时才复制 R 对象（「写时复制」，copy-on-write），而 "multisession" 则是在任何计算前总是把对象复制到相应会话中。"multicore" 后端有一个重大缺点：它在 Windows 系统上不受支持——正因如此，这里的所有示例我们都坚持使用 "multisession" 后端。

一般而言，建议只在重采样的每次迭代至少运行数秒时才考虑并行化。mlr3 有两个选项用于控制执行与粒度：

  • 如果 mlr3.exec_random 被设为 TRUE（默认值），重采样和基准测试中的任务顺序会被随机化。当你在运行具有异构运行时间的基准测试或调优时，这会有所帮助。
  • 选项 mlr3.exec_chunk_size 可用于控制有多少任务被映射到单个 future 上，默认值为 1。该选项的值会被传给 future_mapply()，且 future.scheduling 恒被设为 TRUE。

调整分块大小在某些罕见情况下有助于缓解并行化开销，但在更大的问题或更长的运行时间里不太可能有用。

基准测试可以被看作多个独立重采样的集合，其中任务、学习器和重采样策略的组合定义了要执行的一个重采样。用伪代码表示，该计算可以写成

foreach combination of (task, learner, resampling strategy) {
    foreach resampling iteration {
        execute(resampling, j)
    }
}

因此我们可以选择：

  1. 在所有重采样上并行化，并顺序执行每个重采样（并行化外层循环）；或
  2. 迭代所有重采样，并并行执行每个重采样（并行化内层循环）。

mlr3 通过把所有实验展平到同一层级来简化这一决策，即 benchmark() 迭代外层与内层循环迭代的笛卡尔积元素。因此，你无需决定是要并行化调优还是并行化重采样，你总是同时并行化两者。这种方法使计算变得细粒度，并允许 future 后端把任务分组成合适大小的分块（取决于工作进程数量）；它也使流程与并行化重采样完全一致：

# 简单的基准测试设计
design = benchmark_grid(tsks(c("sonar", "penguins")),
  lrns(c("classif.featureless", "classif.rpart")), rsmp_cv3)

# 启用并行化
future::plan("multisession")

# 并行运行基准测试
bmr = benchmark(design)

对于累计运行时间可能长达数周、数月甚至数年的更大规模基准测试实验，请参阅第 11.2 节。

10.1.3 调优的并行化（Parallelization of Tuning）

调优通常是一个迭代式的流程，由一些本身令人尴尬地可并行的步骤组成。在每次迭代中，调优器（tuner）会提出一批超参数配置（批次大小可以为 1），这些配置随后可以被并行评估。每次迭代后，大多数调优器会根据已获得的性能值以某种方式自我调整。随机搜索与网格搜索是例外，因为它们不根据以往结果选择配置；相反，对这类调优器而言，所有评估都是独立的，原则上可以完全并行化。

调优在 mlr3 中被实现为迭代式基准测试。Tuner 会提出一批学习器，每个学习器在其 $param_set$values 中有不同的配置，批次大小通常可以通过配置参数 batch_size 控制。这个批次会连同调优实例的重采样策略一起传给 benchmark()。

由于每次调用 benchmark() 都依赖于先前的结果，一般不可能在比单个基准测试更高的「层级」上并行化调优。相反，单个 benchmark() 评估会被 mlr3 当作没有调优的实验来并行化。这意味着每个被评估配置的各个重采样迭代都会同时被并行化。要确保充分并行化，请确保 batch_size 乘以重采样迭代次数至少等于可用工作进程数。如果你预期运行时间均匀（即你在调优单个学习器或流水线，且没有任何对运行时间影响很大的超参数），那么以工作进程数的倍数作为目标。一般而言，更大的批次允许更多并行化，而更小的批次意味着更频繁地评估终止条件。无论你是否使用并行化，终止条件只在批次评估之间被检查。

下面的代码展示了随机搜索的并行执行，终止条件设为 20 次迭代、中等批次大小，其中 36 个重采样划分——12 个配置各 3 个划分——在四个工作进程上并行评估。批次大小设为工作进程数的倍数，可确保可用资源得到高效利用。但要注意，调优只在达到给定批次大小的倍数后终止，在本例中是 24 次评估之后。

future::plan("multisession", workers = 4)

instance = tune(
  tnr("random_search", batch_size = 12),
  tsk("penguins"),
  lrn("classif.rpart", minsplit = to_tune(2, 128)),
  rsmp("cv", folds = 3),
  term_evals = 20
)

instance$archive$n_evals
[1] 24

在这个例子中，我们本可以把批次大小增大到 20，从而在恰好达到评估次数时停止，以最有效的方式利用可用资源；但这并不能推广到其他我们无法事先知道评估次数的终止条件。例如，如果我们用 trm("perf_reached") 且批次大小为 12，那么如果批次中第一个配置的性能优于给定阈值，剩余的 11 个配置仍会被不必要地评估。

10.1.4 嵌套重采样的并行化（Nested Resampling Parallelization）

嵌套重采样在概念上可以在三个不同层级并行化，每一层对应不同粒度的任务：

  1. 外层重采样的并行化。此时一个任务就是在外层重采样划分的相应训练集上对学习器进行调优。
  2. 并行评估某次调优迭代提出的超参数配置批次。此时一个任务例如就是对一个配置做交叉验证。
  3. 调优中内层重采样的并行化。此时一个任务就是单个配置的一次训练-预测-评分步骤。

这在下面的伪代码中得到演示，它是 Bischl et al. (2023) 中算法 3 的简化形式：

# 外层重采样，第 1 层：
for (i in seq_len(n_outer_splits)) {
  # 调优实例，在此示例中主要代表 archive
  tuning_inst = ti(...)
  inner_task = get_training_task(task, outer_splits[[i]])
  # 调优循环，其细节取决于所用的调优器
  # 这不对应于某个层级：
  while (!tuning_inst$is_terminated) {
    proposed_points = propose_points(tuning_inst$archive, batch_size)
    # 配置评估，第 2 层：
    for (hp_configuration in proposed_points) {
      split_performances = numeric()
      # 内层重采样，第 3 层：
      for (j in seq_len(n_inner_splits)) {
        split_performances[j] = evaluate_performance(
          learner, hp_configuration, inner_task, inner_splits[[j]]
        )
      }
      performance = aggregate(split_performances)
      update_archive(tuning_inst$archive, configuration, performance)
    }
  }
  evaluate_performance(
    learner, tuning_inst$result, task, outer_splits[[i]]
  )
}

这个算法在 mlr3 中以略高效的方式实现。在第二层（超参数配置的评估）上，它利用了 benchmark() 的功能：为每个提出的超参数配置创建一个 Learner 对象，所有学习器在最内层 for 循环的一个基准测试实验中被重采样，从而有效地把第二层与第三层一起以更细的粒度执行（提出点数量乘以内层重采样迭代次数）。因此，在 mlr3 中并行化嵌套重采样时，用户只需在两个选项中选择：并行化外层重采样，或并行化内层基准测试。

举例来说，让我们使用 AutoTuner（第 4.2 节）和仅两次迭代的随机搜索来调优分类树的 minsplit 参数。注意，这是一个教学示例，用于说明不同并行化层级之间的相互作用，而非现实的配置。我们对内层重采样使用留出法（holdout），并把 batch_size 设为 2，这会在内层基准测试实验中产生两次独立迭代。外层重采样使用五折交叉验证。为简单起见，我们还将忽略 AutoTuner 在调优之后执行的最终模型拟合。下面，我们不加并行化地顺序运行该示例：

library(mlr3tuning)
# 重置为默认的顺序计划
future::plan("sequential")

lrn_rpart = lrn("classif.rpart",
  minsplit  = to_tune(2, 128))

lrn_rpart_tuned = auto_tuner(tnr("random_search", batch_size = 2),
  lrn_rpart, rsmp("holdout"), msr("classif.ce"), 2)

rr = resample(tsk("penguins"), lrn_rpart_tuned, rsmp("cv", folds = 5))

我们现在可以选择并行化外层 CV 或内层基准测试。假设我们有一颗带四个核心（C1-C4）的单 CPU，且调优期间每次内层留出评估耗时四秒。如果我们并行化外层五折 CV（图 10.2），四个核心会先各运行一次外层重采样，第五次迭代的计算必须等待，因为已没有更多可用核心。

# 并行化外层循环
future::plan(list("multisession", "sequential"))

# 备选方案：跳过第 2 级的指定，因为 future
# 默认会把第一级之后的所有级别都设为 "sequential"
future::plan("multisession")

这种方法在图 10.2中说明。四个工作进程各自从计算不同的内层基准测试开始，每个内层基准测试顺序运行，因此在单个工作进程上耗时八秒。由于任务多于工作进程，外层重采样的剩余第五次迭代会排在 C1 上，在前四次迭代于八秒后完成后才执行。在计算第五次外层重采样迭代期间，只有 C1 在忙碌，另外三个核心处于空闲。

相反，如果我们并行化内层基准测试（图 10.3），那么外层重采样顺序运行：五个内层基准测试依次被调度，每个内层基准测试在两个核心上并行运行其两次留出评估；与此同时，C3 和 C4 处于空闲。

# 并行化内层循环
future::plan(list("sequential", "multisession"))

在这个例子中，两种并行化方式都没有充分挖掘四个核心的全部潜力。如果并行化外层循环，所有结果在 16 秒后计算完成；如果并行化内层循环，我们在 20 秒后得到结果；而两种情况下都有一些 CPU 核心在至少一部分时间内闲置。

mlr3 与 future 使两个循环都能启用并行化以实现嵌套并行，甚至可以启用在不同并行化后端上，这在某些分布式计算配置中很有用。注意，对这种嵌套并行化，可用核心的检测无法工作，必须手动设置工作进程数：

# 两个循环都并行运行
future::plan(list(
  tweak("multisession", workers = 2),
  tweak("multisession", workers = 2)
))

这个例子最多会在本地机器上运行四个核心：首先，为外层循环生成两个新会话。两个新会话随后各再生成两个会话用于评估内层基准测试。虽然当第五次外层重采样迭代运行时仍有两个核心空闲，但这种方法把总运行时间降到 12 秒，这在此例中是最优的。

背景与解释（译者注）：嵌套重采样（外层 CV 估计性能、内层 CV 用于调优）的正确并行方式容易搞混。这里三个层级对应三种「任务粒度」：外层一折 = 一次完整调优；一个配置 = 一次内层 CV；内层一折 = 一次训练-预测-评分。mlr3 把调优实现为「迭代式 benchmark」，天然会把第二、三层合并：一个配置的全部内层迭代作为一个整体进入 benchmark()。实践中通常只需二选一：并行外层（每 worker 各自完整调优一次）适合调优本身较重的情形；并行内层（各 worker 并行评估不同配置）适合配置评估较重的情形。书中数字可这样核对：并行外层时，前 4 个外层折各需 8 秒（2 配置 × 4 秒），第 5 折再花 8 秒，共 16 秒；并行内层时，每折的 2 个配置并行占 2 核、耗时 4 秒，5 折顺序执行共 20 秒；两层都并行时每层各 2 worker，每折 4 秒、两折一组并行，总耗时 12 秒。

10.1.5 预测的并行化（Parallelization of Predictions）

最后，单个学习器的预测可以并行化，因为多个观测的预测是相互独立的。对大多数学习器而言，训练才是瓶颈，并行化预测并不值得，但也会有例外，例如当你的测试数据集非常大时。

要并行预测，首先把测试数据分成多个组，然后用经由 plan() 配置的激活后端，把学习器的 predict 方法并行应用到每个组。在第二步中，得到的预测在内部被合并。为避免意外地并行预测，必须通过学习器的 parallel_predict 字段显式启用并行预测：

# 在 sonar 任务上训练随机森林
tsk_sonar = tsk("sonar")
lrn_rpart = lrn("classif.rpart")
lrn_rpart$train(tsk_sonar)

# 在四个工作进程上设置并行预测
future::plan("multisession", workers = 4)
lrn_rpart$parallel_predict = TRUE

# 预测
prediction = lrn_rpart$predict(tsk_sonar)

10.1.6 使用 mirai 进行并行化（Parallelization with mirai）（+）

mirai 包是一个替代的并行化后端，它启动被称为 daemon（守护进程）的持久 R 会话。与 future 包相比，mirai 每个任务的开销显著更低，这在训练许多快速拟合的模型时尤其有利。手动分块不再必要，因为 mirai 的分发器（dispatcher）会自动在可用 daemon 之间分配任务。

要并行化计算，用 daemons() 启动 daemon。计算档案（compute profile）必须设为 "mlr3_parallelization"。为让 mirai 的结果可重现，请在创建 daemon 时设置 seed。对于本地 daemon，你可以用 output = TRUE 把日志消息重定向到主会话。

mirai::daemons(2, .compute = "mlr3_parallelization", seed = 7832L, output = TRUE)

tsk_sonar = tsk("sonar")
lrn_rpart = lrn("classif.rpart")
rsmp_cv3 = rsmp("cv", folds = 3)
system.time({resample(tsk_sonar, lrn_rpart, rsmp_cv3)})
   user  system elapsed 
  0.029   0.000   0.451

mirai 也支持嵌套配置。只要在主 R 会话中配置了 daemon，外层循环就会并行运行，而内层循环在每个 daemon 上顺序运行。

mirai::daemons(5, .compute = "mlr3_parallelization")

lrn_rpart_tuned = auto_tuner(
  tuner = tnr("random_search", batch_size = 2),
  learner = lrn("classif.rpart", minsplit = to_tune(2, 128)),
  resampling = rsmp("cv", folds = 3),
  measure = msr("classif.ce"),
  term_evals = 2
)

rr = resample(tsk("penguins"), lrn_rpart_tuned, rsmp("cv", folds = 5))

要同时并行化外层和内层循环，使用 everywhere() 为内层循环配置 daemon。

mirai::daemons(5, .compute = "mlr3_parallelization")

mirai::everywhere({
  mirai::daemons(3, .compute = "mlr3_parallelization")
}, .compute = "mlr3_parallelization")

背景与解释（译者注）：future 与 mirai 是两种设计哲学的并行后端：future 以「全局抽象 + 惰性求值」出名，一次 plan() 后整个生态共享同一后端，代价是每个 future 需要额外的调度与序列化开销；mirai 则采用「常驻 daemon + 统一分发器」，daemon 启动一次后持续复用，任务直接投递，单任务开销远低于 future，尤其适合训练大量小模型（如调优中评估许多快速配置）的场景。注意 mirai 需要显式设置 .compute = "mlr3_parallelization" 档案，这样 mlr3 才会识别并使用它；everywhere() 让内层循环的每个 worker 再派生自己的 daemon，实现双层并行。两种后端都建议设置随机种子以保证可重现性（future 用 set.seed，mirai 用 daemons(seed=)）。

10.2 错误处理（Error Handling）

在大型实验中，模型拟合或预测失败并报错并不罕见。这是因为算法必须处理任意的数据，并非所有可能情况都能得到处理。虽然我们试图在执行前识别出明显的问题（例如对无法处理缺失值的学习器出现缺失值），但其他问题则更难检测。例如可能引起训练问题的数值困难（比如不收敛），或者预测步骤中出现分类变量的新水平。不同学习器在遇到这类问题时的表现差异很大：有些模型在训练步骤中会发出「拟合失败」的警告，但返回一个基线模型；其他模型则会停止执行。在预测期间，有些学习器会报错并拒绝为无法处理的观测预测响应，另一些则可能预测出 NA。在本节中，我们将讨论在我们不希望程序停止时（例如在基准测试实验期间）如何防止这些错误导致程序停止。

10.2.1 封装（Encapsulation）

封装（encapsulation）确保被发出的条件（例如消息、警告和错误）被截获，并且训练或预测步骤中引发的所有条件都会被记录到学习器中，而不会中断程序流程。这意味着模型可以用于拟合和预测，任何条件都可以事后分析。然而，实验的结果将是一个缺失的模型和/或缺失的预测，具体取决于错误发生的位置。在第 10.2.2 节中，我们将讨论用回退学习器（fallback learner）替换缺失模型和/或预测。

每个 Learner 都有方法 $encapsulate() 来控制 train 或 predict 步骤如何被包装。第一种封装执行方式由 evaluate 包提供，它评估 R 表达式并捕获和跟踪条件（输出、消息、警告或错误），而不让它们终止进程（完整细节见 encapsulate() 的文档）：

$encapsulate()
# 在训练中触发警告和错误
lrn_debug = lrn("classif.debug", warning_train = 1, error_train = 1)

# 为 train() 和 predict() 启用封装
lrn_debug$encapsulate("evaluate", fallback = lrn("classif.featureless"))
lrn_debug$train(tsk_penguins)

注意，封装会捕获所有写入标准输出（stdout）和标准错误（stderr）流的输出，并把它们存储在学习器的日志中。然而，在某些计算设置中，调用进程需要对日志输出进行操作，例如第 11 章中的 batchtools 包。在这种情况下，请改用封装方法 "try"，它会捕获被发出的条件，但不会抑制输出。

缺失的学习器和/或预测在诸如重采样、基准测试或调优等自动化流程中尤其成问题（第 5.1.1 节），因为结果无法在各迭代间正确地聚合。在下一节中，我们将考察回退学习器，它负责插补缺失的模型和预测。

背景与解释（译者注）：封装（encapsulation）的思想是把「触发错误」与「让错误中断整个实验」分离。R 本身就有条件（condition）机制——message()、warning()、stop() 分别发出消息、警告和错误，默认行为是错误会中断执行。mlr3 的三种封装方式各有用武之地："evaluate" 在同一进程内捕获条件（最轻量，但无法隔离段错误，也无法中断卡死的 C 代码）；"callr" 把训练/预测放进独立 R 进程（能防段错误，也支持可靠超时，但每个任务要付一次进程启动成本）；"try" 则只捕获条件但保留输出流，供 batchtools 等外部调度器读取。特别提醒：模型「跑飞」（不收敛、死循环）靠超时（$timeout）兜底，而这一步最好配合 callr，因为纯 R 层面的 evaluate 无法抢占已卡在编译代码中的线程。

10.2.2 回退学习器（Fallback Learners）

假设重采样期间在一次或多次迭代中训练模型时发生了错误，那么继续我们的实验有三种方法：

  1. 忽略失败的迭代——这可能是实践中最常用的做法，然而它在统计上不成立。假设我们试图评估一个模型的性能。如果在某些重采样划分中，预测时出现了训练时没见过的因子水平，导致模型无法处理它们而报错，那么这个模型可能会出错。如果我们丢弃失败的迭代，我们的模型看起来会表现得很好，尽管它实际上无法对一整类特征做出预测。
  2. 惩罚失败的学习器——与其忽略失败的迭代，不如插补最差的可能得分（由给定的 Measure 定义），从而对失败的学习器进行重罚。然而，这往往对许多问题过于严厉，而且对某些度量而言，没有合理的值可以插补。
  3. 用回退学习器进行训练和预测——与其用最差得分插补，不如训练一个基线学习器，并用这个模型做出预测。
回退学习器（Fallback Learner）

我们强烈推荐最后一种方案，它在统计上成立，并且可以在任何实际实验中轻松使用。mlr3 包含两个基线学习器：lrn("classif.featureless")（在其默认配置下总是预测多数类）和 lrn("regr.featureless")（默认预测平均响应）。

为了让这个过程在重采样和基准测试期间更方便，我们支持通过把一个 Learner 传给 $encapsulate() 来拟合一个基线（虽然理论上你可以使用任何 Learner）作为回退学习器。在下一个例子中，我们给 debug 学习器加上一个分类基线，这样当 debug 学习器出错时，mlr3 会在内部回退到 featureless 学习器的预测。

$encapsulate()
lrn_debug = lrn("classif.debug", error_train = 1)
lrn_debug$encapsulate("evaluate", fallback = lrn("classif.featureless"))

10.2.3 条件类（Condition Classes）

mlr3 使用自定义条件类来对错误和警告进行分类。这些类决定封装和回退学习器的行为。

以下是可用的错误类（完整细节见 mlr_conditions）：

  • error_mlr3() – 所有与 mlr3 相关的错误的基础错误类。
  • error_config() – 表示用户配置错误，例如无效的学习器设置。
  • error_input() – 表示无效输入。
  • error_timeout() – 表示封装期间出现超时。
  • error_learner() – 表示一般的学习器错误。
  • error_learner_train() – 表示学习器在训练期间失败。
  • error_learner_predict() – 表示学习器在预测期间失败。

默认情况下，Mlr3ErrorConfig 类的错误总是立即传播，即使封装处于激活状态。配置错误表明存在应该修复的设置 bug，而不是由回退学习器静默处理。所有其他错误（例如 Mlr3ErrorLearnerTrain 或 Mlr3ErrorTimeout）都会被捕获，并改用回退学习器。

这种默认行为可以通过向 $encapsulate() 传递一个 when 函数来定制。这个函数接收条件对象（cond）和阶段（"train" 或 "predict"），如果应该使用回退则返回 TRUE，如果错误应该传播则返回 FALSE。例如，让超时错误也传播而不是回退：

lrn_debug = lrn("classif.debug", error_train = 1)
lrn_debug$encapsulate(
  "evaluate",
  fallback = lrn("classif.featureless"),
  when = function(cond, stage) !inherits(cond, "Mlr3ErrorTimeout")
)

10.3 日志（Logging）

mlr3 使用 lgr 包来控制输出的详细程度，即决定运行 mlr3 操作时显示多少输出——从抑制所有非关键消息，到调试用的详细消息。在本节中，我们将介绍如何更改日志级别、重定向输出，以及最后更改日志反馈的时机。

10.3.1 日志器层级（Logger Hierarchy）

mlr3 生态系统使用层级日志系统。基础日志器名为 "mlr3"，是生态系统中所有日志器的父级。每个包在这个基础日志器下注册自己的子日志器：

  • "mlr3" – 整个 mlr3 生态系统的基础日志器。
  • "mlr3/core" – 核心 mlr3 包的子日志器。
  • "mlr3/bbotk" – bbotk 的子日志器，也被 mlr3tuning 和 mlr3fselect 使用。
  • "mlr3/mlr3pipelines" – mlr3pipelines 的子日志器。

在基础 "mlr3" 日志器上设置阈值，可以控制整个生态系统的日志级别。子日志器继承其父级的阈值，但也可以独立配置。这使得一次性静默所有日志，或选择性地为特定包启用日志变得很容易。

10.3.2 更改日志级别（Changing Log Levels）

mlr3 使用 lgr 的以下详细级别：

  • "warn" – 只记录非破坏性警告
  • "info" – 记录模型运行时间等信息，以及警告
  • "debug" – 记录调试用的详细消息，以及信息和警告

mlr3 中的默认日志级别是 "info"，这意味着只显示有信息价值或更严重的消息，即 "info" 和 "warn"。

要更改日志阈值，你需要从 lgr 中取出 R6 日志器对象，然后调用 $set_threshold()。要为整个生态系统更改阈值，请在基础日志器上设置它：

lgr::get_logger("mlr3")$set_threshold("debug")

或者抑制除警告外的所有消息：

lgr::get_logger("mlr3")$set_threshold("warn")

因为子日志器继承其父级的阈值，这会静默生态系统中所有包。要选择性控制日志，请在各个子日志器上设置阈值。例如，要禁用核心 mlr3 包的日志，但保留 mlr3tuning 的日志：

lgr::get_logger("mlr3/core")$set_threshold("warn")
lgr::get_logger("mlr3/bbotk")$set_threshold("info")

10.3.3 重定向日志输出（Redirecting Log Output）

默认情况下，lgr 的输出打印在控制台中，但你可以选择以各种格式把它重定向到文件，例如重定向到 JSON 文件：

tf = tempfile("mlr3log_", fileext = ".json")

# 以 R6 对象形式获取日志器
logger = lgr::get_logger("mlr3")

# 添加 Json appender
logger$add_appender(lgr::AppenderJson$new(tf), name = "json")

# 发出一个警告
logger$warn("this is a warning from mlr3")

# 打印文件内容（分成两行显示）
x = readLines(tf)
cat(paste0(substr(x, 1, 71), "\n", substr(x, 72, nchar(x))))
{"level":300,"timestamp":"2026-09-24 11:58:13","logger":"mlr3","caller"
:"eval","msg":"this is a warning from mlr3"}
# 再次移除 appender
logger$remove_appender("json")

更全面的示例请参阅 lgr 中的 vignette。

10.3.4 调试模式（Debug Mode）

当使用并行化和/或封装时，日志可能被延迟、乱序，或在某些错误的情况下完全缺失。当需要即时访问日志消息时（例如调试时），可以选择禁用 future 和封装。要启用「调试模式」，设置 options(mlr3.debug = TRUE)，并确保学习器的 $encapsulate 槽被设为 "none"（默认值）或 "evaluate"。调试模式只应在调试期间启用，不应在生产环境中使用，因为它会禁用并行化并导致无法重现的意外 RNG 行为。

背景与解释（译者注）：lgr 是 mlr3 生态的日志基础设施，其设计借鉴了 Java 的 log4j/SLF4J：logger 构成树状层级（父阈值默认被子级继承），appender 决定每条记录写到哪里（控制台、文件、JSON、数据库等），layout 决定输出格式。常用操作是：想安静就跑 set_threshold("warn")，想排查就 set_threshold("debug")，想审计就把 JSON appender 挂到文件。注意「debug 模式」与「debug 日志级别」是两回事——前者（options(mlr3.debug = TRUE)）强制串行执行并暴露原始错误栈，便于定位 bug，但因绕过了 future 的并行随机种子管理，会导致结果不可重现，所以只能在调试期临时开启。日志级别阈值是「>= 才输出」的排序：warn < info < debug，设 info 会同时显示 warn，设 warn 则只留警告。

10.4 数据后端（Data Backends）

Task 对象将其数据存储在一个抽象的数据对象中，即DataBackend。数据后端提供统一的 API 来获取数据的子集或查询其信息，无论数据在系统中如何存储。默认后端通过 DataBackendDataTable 类使用 data.table，作为一个非常快速高效的内存数据库。

虽然将任务数据存储在内存中对模型拟合时的访问最为高效，但有两个主要的缺点：

  1. 即使只需要一小部分数据，例如在做子采样时，整个数据集也会驻留在内存中并消耗内存。这在处理大数据任务或同时处理许多任务（例如基准测试）时尤其是个问题。
  2. 在并行化（第 10.1 节）期间，完整的数据需要被传输到 worker，这会增加开销。

为了避免这些缺点，特别是对于较大的数据，可能需要接入外存（out-of-memory）数据以降低内存需求。这样一来，只有学习器当前所需的那部分数据才会被放入主内存进行操作。处理这个问题有多种选项：

  1. DataBackendDplyr，它对接 R 包 dbplyr，将 dplyr 扩展到许多流行的 SQL 数据库上，如 MariaDB、PostgresSQL 或 SQLite。
  2. DataBackendDuckDB 用于通过 duckdb 连接的 DuckDB 数据库，这是 SQLite 的一种快速、零配置的替代方案。
  3. DataBackendDuckDB 用于 Parquet 文件。这意味着数据无需转换为 DuckDB 的原生存储格式，你可以直接在包含一个或多个流行 Parquet 格式文件的目录上工作。

下面，我们将展示如何使用 mlr3db 来处理这些选项中的每一个。

背景与解释（译者注）：默认情况下 mlr3 的任务数据存在内存中的 data.table 里，访问快但有两个隐患：一是只要任务存在，整个数据集就常驻内存（即使子采样只用 2%）；二是并行化时每个 worker 都要拷贝一份完整数据。mlr3db 把数据搬到 SQLite/DuckDB 或 Parquet 文件里，让「内存中的镜像」按需懒加载，学习器当前迭代需要多少就取多少，用完交给垃圾回收器释放。这样大数据也能跑在内存有限的环境里，代价是每次数据访问多一次查询开销，因此更适合「大而稀疏」的取数场景。注意：这种后端只「看到」你传入的数据，预先过滤掉的列和行它并不知晓。

10.5 扩展 mlr3 并定义一个新的 Measure

读到这里，你已经快要成为一名 mlr3 专家了，甚至可能想向我们的世界中添加更多类。虽然许多类都可以扩展，但它们都有相似的设计接口，因此，我们只演示如何创建自定义的 Measure。如果你对实现新的学习器、PipeOp 或调优器感兴趣，那么请查看相应包中的 vignette：mlr3extralearners、mlr3pipelines 或 mlr3tuning。如果你正在考虑创建一个添加全新任务类型的包，欢迎通过 GitHub、电子邮件或 Mattermost 与我们联系寻求支持。本节假定你已对 R6 有良好了解，请参阅第 1.5.1 节获得简要介绍及更多资源的参考。

背景与解释（译者注）：Measure 是 mlr3 中评估预测质量的统一抽象：它以 R6 类的形式封装了评分函数及其元数据（ID、取值范围、优化方向、需要的预测类型等），从而使「分数」可以被量尺、重采样、调优和基准测试统一使用。R6 是 R 的引用类（reference class）实现，类的「方法」写在 public/private 列表中，super$initialize() 调用父类构造器。定义新度量最核心的两件事：一是在 $initialize() 里说清楚元数据（id、packages、properties、predict_type、range、minimize）；二是实现私有的 .score() 方法完成实际计算。写完类之后，既可以 MeasureRegrThresholdAcc$new() 直接实例化，也可以注册进 mlr_measures 字典，之后就能用 msr() 糖函数按字符串 id 取用。

作为一个例子，让我们考虑一个回归度量：如果真实值与预测值之差小于真值的一个标准差，则将该预测评分为 1，否则评分为 0。用数学语言可定义为 \(f(y, \hat{y}) = \frac{1}{n} \sum_{i=1}^n \mathbb{I}(|y_i - \hat{y}_i| < \sigma_y)\)，其中 \(\sigma_y\) 是真值的标准差，\(\mathbb{I}\) 是指示函数。在代码中，这个度量可以写成：

threshold_acc = function(truth, response) {
  mean(ifelse(abs(truth - response) < sd(truth), 1, 0))
}

threshold_acc(c(100, 0, 1), c(1, 11, 6))
[1] 0.6667

根据此度量的定义，其值的范围在 \([0, 1]\) 内，其中 \(1\) 的完美分数意味着所有预测都在真值的一个标准差之内，因此对于这个度量，分数越大越好。

要在 mlr3 中使用这个度量，我们需要创建一个新的 R6Class，它将继承自 Measure，在这种情况下具体继承自 MeasureRegr。这个新度量的代码在下面的代码片段中，后面附有解释。这个代码块可以用作大多数性能度量的模板。

MeasureRegrThresholdAcc = R6::R6Class("MeasureRegrThresholdAcc",
  inherit = mlr3::MeasureRegr, # regression measure
  public = list(
    initialize = function() { # initialize class
      super$initialize(
        id = "thresh_acc", # unique ID
        packages = character(), # no package dependencies
        properties = character(), # no special properties
        predict_type = "response", # measures response prediction
        range = c(0, 1), # results in values between (0, 1)
        minimize = FALSE # larger values are better
      )
    }
  ),

  private = list(
    # define score as private method
    .score = function(prediction, ...) {
      # define loss
      threshold_acc = function(truth, response) {
        mean(ifelse(abs(truth - response) < sd(truth), 1, 0))
      }
      # call loss function
      threshold_acc(prediction$truth, prediction$response)
    }
  )
)
  1. 在前两行中，我们为类命名，这里为 MeasureRegrThresholdAcc，然后声明这是一个继承自 MeasureRegr 的回归度量。
  2. 我们通过声明其唯一 ID 为 "thresh_acc"、它不需要任何外部包（packages = character()）并且没有特殊属性（properties = character()）来初始化该类。
  3. 然后我们传入损失函数的具体细节：它衡量 "response" 类型预测的质量，其值范围在 (0, 1) 之间，并且损失在其最大值处被优化（minimize = FALSE）。
  4. 最后，我们将评分本身定义为一个名为 .score 的私有方法，在方法中我们将预测传递给上面定义的函数。

有时度量需要来自训练集、任务或学习器的数据。这些通常是复杂的边界情况示例，因此我们不会在这里详细讨论，对于可运行的示例，我们建议查看 MeasureSurvSongAUC 和 MeasureSurvAUC 的代码。你也可以查阅 Measure 的手册页，了解可以指定的其他属性和元数据的概述。

定义好度量后，你可以用 R6 构造器（$new()）加载它，或者通过将其添加到 mlr_measures 字典，使其可用于 msr() 糖函数构造：

tsk_mtcars = tsk("mtcars")
split = partition(tsk_mtcars)
lrn_featureless = lrn("regr.featureless")$train(tsk_mtcars, split$train)
prediction = lrn_featureless$predict(tsk_mtcars, split$test)
prediction$score(MeasureRegrThresholdAcc$new())

# 或者通过向第一个参数传递唯一键、向第二个参数传递类来添加到字典

虽然我们只介绍了如何创建一个简单的回归度量，但向我们的世界中添加其他类的过程本质上是相同的：

  1. 找到要继承的正确类
  2. 添加方法：
    1. 以正确的属性初始化对象（$initialize()）。
    2. 实现进行实际计算的方法。在上面的例子中，这是私有的 $.score() 方法。

10.6 结论（Conclusion）

本章涵盖了几个高级主题，包括并行化、错误处理、日志、处理数据库以及扩展 mlr3 世界。对于简单的用例，你可能不需要详细了解每个主题，但是，我们建议至少熟悉错误处理和回退学习器，因为这些对于防止即使是简单的实验被打断也是必不可少的。如果你正在处理大型实验或数据集，那么理解并行化、日志和数据库也将是必不可少的。

我们没有深入地涵盖这些主题，因此如果你想更多地了解这些领域，我们推荐以下资源。如果你有兴趣了解更多关于 R 中并行化的知识，我们推荐 Schmidberger et al. (2009) 和 Eddelbuettel (2020)。想了解更多关于日志的信息，请阅读 lgr 中的 vignette，它们涵盖了从记录日志到 JSON 文件再到检索记录对象以进行调试的所有内容。有关 R 中可用 DBMS 的概述，请参见 https://cran.r-project.org/view=Databases 上的数据库 CRAN 任务视图，特别是 dbplyr 包中关于 mlr3 中现成可用的 DBMS 的 vignette。

  1. 考虑下面的例子：你使用 multisession 后端在四个 worker 上重采样一个学习器（debug 学习器，在训练期间休眠三秒）：

  2. 通过测量经过的时间来证明你的观点，例如使用 system.time()。
  3. 你会在设置中改变什么以及为什么？

  1. 创建一个新的自定义二分类度量，对（"prob" 类型的）预测进行评分。该度量应计算正类预测概率与 0-1 编码的真实标签之间的绝对差，然后在测试集上对这些值取平均。使用 tsk("sonar") 上的 classif.log_reg 进行测试。

  2. 在从 0 到 1 的连续区间上「调优」classif.debug 学习器的 error_train 超参数，使用简单的分类树作为回退学习器，并使用 penguins 任务。使用随机搜索和 10 折交叉验证调优 50 次迭代。检查生成的 archive，找出哪些评估出现了错误，哪些没有。现在在 0.3 到 0.7 的区间内做同样的事情。你的结果令人惊讶吗？

背景与解释（译者注）：练习 3 是本章最值得动手的一题：error_train 是 classif.debug 的「注入错误率」，用来人为制造训练失败。把它当作连续超参数放进调优范围，再用分类树做回退学习器，就能直观看到：当调优采样到会让训练报错的参数组合时，mlr3 会静默切换到回退模型，实验不中断。检查 archive 时可以用 rbindlist(archive$data)[, .(error_train, classif.rpart)] 之类的方式对照参数与错误标记；把区间缩窄到 0.3–0.7 后「错误大多消失」正是回退与错误封装机制起作用的证据——这也是生产环境里「健壮实验」的标准做法。
