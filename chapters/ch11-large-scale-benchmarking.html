大规模基准测试（Large-Scale Benchmarking）

《Applied Machine Learning Using mlr3 in R》中文翻译 · 章节 第 11 章 大规模基准测试

Sebastian Fischer
慕尼黑路德维希-马克西米利安大学（Ludwig-Maximilians-Universität München）及慕尼黑机器学习中心（Munich Center for Machine Learning, MCML）

Michel Lang
可信数据科学与安全研究中心（Research Center Trustworthy Data Science and Security），多特蒙德工业大学（TU Dortmund University）

Marc Becker
慕尼黑路德维希-马克西米利安大学（Ludwig-Maximilians-Universität München）及慕尼黑机器学习中心（Munich Center for Machine Learning, MCML）

在机器学习中，仅靠数学分析往往难以评估方法。即使形式化分析能够成功应用，真实数据集是否满足定理成立的假设，也常常是一个悬而未决的问题。经验基准（empirical benchmark）实验在广泛的数据集上评估不同算法的性能。这些实证研究对于理解现有方法的能力与局限、以及开发新的改进方法至关重要。可信的基准实验通常是大规模的（large-scale），这意味着它们可能使用大量的数据集、度量与学习器。此外，数据集必须覆盖广泛的领域与问题类型，因为结论只能推广到基准研究所覆盖的那类数据集上。

背景与解释（译者注）：机器学习方法的评估很难仅靠数学分析完成——真实数据往往不满足定理所需的严格假设，而经验基准（empirical benchmark）实验通过在多个数据集上比较不同算法的性能，直接回答「在哪些数据上、哪种方法更有效」的问题。这也是 OpenML 这类共享平台存在的根本动机：只有结论覆盖尽可能多样的数据领域与问题类型，研究结论才具有可推广性。

大规模基准实验包含三个主要步骤：获取实验数据、执行实验、分析结果；我们将逐一讨论这些步骤。在11.1 节中，我们将首先讨论mlr3oml，它提供了mlr3与 OpenML (Vanschoren et al. 2013)之间的接口，OpenML 是一个流行的数据集上传与下载工具。增加数据集的数量会带来「大规模」实验，可能需要可观的计算资源，因此在11.2 节中，我们将介绍mlr3batchmark，它把 mlr3 与batchtools (Lang, Bischl, and Surmann 2017)连接起来，后者提供了在高性能计算（HPC）集群上管理与执行实验的方法。最后，在11.3 节中，我们将演示如何利用mlr3benchmark对大规模基准实验的结果进行形式化分析。

在本章中，我们将沿用 Couronné、Probst 与 Boulesteix (2018)中的贯穿示例，对随机森林模型与逻辑回归进行基准比较。我们还假定你已经阅读过第 7 章和第 10 章。我们使用 ppl("robustify")（9.4 节）来自动化常见的预处理步骤。我们还把无特征（featureless）基线设置为回退学习器（fallback learner）（10.2.2 节），并把 "try" 作为我们的封装（encapsulation）方法（10.2.1 节），它会将错误/警告记录到外部文件中，该文件可被 batchtools 读取（我们将在11.2.3 节回到这一点）。

# 无特征基线（featureless baseline）
lrn_baseline = lrn("classif.featureless", id = "featureless")

# 逻辑回归流水线
lrn_lr = lrn("classif.log_reg")
lrn_lr = as_learner(ppl("robustify", learner = lrn_lr) %>>% lrn_lr)
lrn_lr$id = "logreg"
lrn_lr$encapsulate("try", fallback = lrn_baseline)

# 随机森林流水线
lrn_rf = lrn("classif.ranger")
lrn_rf = as_learner(ppl("robustify", learner = lrn_rf) %>>% lrn_rf)
lrn_rf$id = "ranger"
lrn_rf$encapsulate("try", fallback = lrn_baseline)

learners = list(lrn_lr, lrn_rf, lrn_baseline)

作为起步示例，我们将使用精度（accuracy）与三折交叉验证，在三个分类任务上比较我们的学习器。

design = benchmark_grid(tsks(c("german_credit", "sonar", "diabetes")),
  learners, rsmp("cv", folds = 10))
bmr = benchmark(design)
bmr$aggregate(msr("classif.acc"))[, .(task_id, learner_id, classif.acc)]

1: german_credit      logreg      0.7460
2: german_credit      ranger      0.7630
3: german_credit featureless      0.7000
4:         sonar      logreg      0.7162
5:         sonar      ranger      0.8412
6:         sonar featureless      0.5329
7:      diabetes      logreg      0.7461

9:      diabetes featureless      0.6354

在这个小型实验中，随机森林在全部三个数据集上似乎都优于其他学习器。然而，这一分析并不具有决定性，因为我们只考虑了三个任务，而且性能差异可能在统计上并不显著。下面，我们将介绍一些改进该研究的技巧。

背景与解释（译者注）：原文此处称「使用精度（accuracy）与三折交叉验证（three-fold CV）」，而下方代码实际使用了 10 折交叉验证（folds = 10），存在笔误，应以代码为准，即对每个数据集使用 10 折交叉验证。此外，仅凭 3 个数据集上的精度差异不足以断言随机森林更优——这既是因为数据集太少、抽样波动大，也是因为需要对多个数据集上的表现做统计检验（见 11.3 节）。这正是本章后续引入 OpenML、大规模基准测试与统计检验的动机。

11.1 用 OpenML 获取数据（Getting Data with OpenML）

要从基准实验中得出有意义的结论，数据集与任务的良好选择至关重要。OpenML 是一个开源平台，它以标准化格式促进机器学习研究数据、算法与实验结果的共享与传播，从而支持跨研究的一致比较。OpenML 的设计确保平台上的所有数据都符合「FAIR」原则（Findability 可发现性、Accessibility 可访问性、Interoperability 可互操作性、Reusability 可复用性），保证数据易于被发现和重用。平台上的所有实体都有唯一标识符和标准化的（元）数据，可通过 REST API 或网页界面访问。

OpenML

背景与解释（译者注）：OpenML 是机器学习领域最早也最著名的数据与实验共享平台之一（2013 年发布），其「FAIR」原则（可发现、可访问、可互操作、可复用）与当前的开放科学运动一脉相承。每个数据集、任务、算法与实验结果都有唯一 ID 与标准化元数据，REST API 使程序化访问成为可能。对于中文研究者而言，OpenML 提供的开源数据集（如 adult、german_credit 等）也常被用来复现论文实验；但需注意部分数据集的元数据由社区维护，使用前应核对数据规模与许可。

在本节中，我们将介绍 OpenML 的一些主要功能，以及如何通过 mlr3oml 接口包来使用这些功能。具体来说，我们将讨论 OpenML 的数据集、任务与任务集合，但不会涉及算法或实验结果。

11.1.3 任务集合（Task Collection）

OpenML 任务集合是一个打包现有任务的容器对象。这允许创建基准套件（benchmark suite），即满足一定质量标准的精选任务集合。例子包括 OpenML CC-18 基准套件 (Bischl et al. 2021)、AutoML 基准 (Gijsbers et al. 2022)以及表格深度学习基准 (Grinsztajn, Oyallon, and Varoquaux 2022)。OMLCollection 对象用 ocl() 加载，例如我们将查看 ID 为 99 的 CC-18：

ocl()

背景与解释（译者注）：基准套件（benchmark suite）是一组经过人工筛选、满足质量门槛（如样本量、缺失率、类别数、元数据完整性）的任务集合。直接使用套件可以避免研究者「挑选」对自己方法有利的数据集——即所谓的选择偏差（selection bias），也让不同论文的实验结果可以横向比较。CC-18 是 OpenML 上最常用的分类基准套件之一；AutoML 基准（AMLB）与表格深度学习基准则分别服务于自动机器学习与深度学习研究。

otask_collection = ocl(id = 99)
otask_collection
<OMLCollection: 99> OpenML-CC18 Curated Class[...]
 * data:  72
 * tasks: 72

该任务集合包括 72 个基于不同数据集的分类任务，可以通过 $task_ids 访问：

otask_collection$task_ids[1:5] # 集合中的前 5 个任务
[1]  3  6 11 12 14

任务集合可用于在 mlr3 中快速定义基准实验。要方便地从基准套件构造所有任务与重采样，可以分别使用 as_tasks() 和 as_resamplings()：

tasks = as_tasks(otask_collection)
resamplings = as_resamplings(otask_collection)

或者，如果我们想进一步筛选集合，例如筛选到一个包含六个任务的二分类实验，我们可以用 CC-18 集合中的任务 ID 作为 task_id 参数运行 list_oml_tasks()。我们可以使用 list_oml_tasks() 的参数来要求类别数为 2，也可以利用 list_oml_tasks() 的返回结果是 data.table 这一事实，对结果表取子集。

binary_cc18 = list_oml_tasks(
  limit = 6,
  task_id = otask_collection$task_ids,
  number_classes = 2
)

我们现在定义用于比较逻辑回归与随机森林学习器的任务与重采样。注意该集合中所有重采样都恰好包含 10 次迭代。

# 以列表形式加载任务
otasks = lapply(binary_cc18$task_id, otsk)

# 转换为 mlr3 任务与重采样
tasks = as_tasks(otasks)
resamplings = as_resamplings(otasks)

为了定义设计表，我们使用 benchmark_grid() 并把 paired 设为 TRUE，这用于每个重采样都在相应任务上实例化的情形（因此下面的 tasks 与 resamplings 长度必须相同），且每个学习器都应在每个重采样任务上被评估。

large_design = benchmark_grid(tasks, learners, resamplings,
  paired = TRUE)

11.2 在 HPC 集群上进行基准测试（Benchmarking on HPC Clusters）

正如10.1 节所讨论的，基准实验的并行化很简单，因为它们是令人尴尬地并行（embarrassingly parallel）的。然而，对于大型实验，在高性能计算（HPC）集群上进行并行化往往更可取。batchtools 提供了一个框架，用于在此类站点上从 R 并行运行大批量计算实验。它非常灵活，适用于广泛的计算实验，包括机器学习、优化、模拟等。

高性能计算（High-performance Computing）
"batchtools" 作为 future 的后端

在10.1.2 节中我们提到过不同的并行化后端。包 future 包含一个 "batchtools" 计划（plan），但它不提供直接使用 batchtools 所带来的额外控制。

HPC 集群是相互连接的计算机或服务器的集合，提供超越单台计算机的计算能力。HPC 集群通常由多个计算节点（compute node）组成，每个节点拥有多个 CPU/GPU 核心、内存和本地存储。这些节点通常通过高速网络与网络文件系统相连，使节点能够通信并协同完成给定任务。HPC 集群与个人计算机（PC）最重要的区别在于：节点往往无法被直接访问，计算作业由调度系统（如 Slurm，Simple Linux Utility for Resource Management，简单 Linux 资源管理工具）排队。调度系统是一种软件工具，负责在集群上把计算资源分配给用户或应用程序。它确保多个用户和应用程序能够公平且高效地访问集群资源，同时也有助于最大化计算资源的利用率。

背景与解释（译者注）：高性能计算集群（HPC cluster）由登录节点（head node）、计算节点（compute node）与共享文件系统组成。与个人电脑最大的不同是，用户不能直接「登录」计算节点运行程序，而是把作业（job）提交给调度系统（如 Slurm、PBS/Torque、LSF），由调度系统按公平与效率原则排队分配资源。理解这一「提交-排队-执行」模型，是理解 batchtools 中 registry、cluster function、template 等概念的前提。对于在国内超算中心（如国家超算中心、各高校集群）使用 R 的用户，同样遵循这一模式，只是调度命令不同。

图 11.1 给出了 HPC 架构的粗略示意图。多个用户可以登录头节点（通常通过 SSH），并通过发送「用资源 Y 执行计算 X，持续 Z 时间」形式的命令把计算作业加入队列。调度系统控制这些计算作业何时执行。

在本节剩余部分，我们将介绍如何使用 batchtools 和 mlr3batchmark 来提交作业、让作业适配集群、保证可复现性、查询作业状态以及调试失败。

11.2.1 实验注册表设置（Experiment Registry Setup）

batchtools 围绕实验或「作业（job）」构建。一个作业的重复执行（replication）由把一个（参数化的）算法应用于一个（参数化的）问题来定义。batchtools 中的基准实验由许多这样的实验组成，这些实验使用不同的算法、算法参数、问题与问题参数。每个这样的实验在计算上独立于其他所有实验，构成 batchtools 可以并行化的基本计算层级。在本节中，我们将一个 batchtools 实验定义为一个学习器在一个任务上的一个重采样迭代；在11.2.4 节中，我们将考察定义实验的不同方式。

运行实验的第一步是用 makeExperimentRegistry() 创建实验注册表，或用 loadRegistry() 加载实验注册表。这构造了 batchtools 中所有函数之间的通信对象，并对应于文件系统上的一个文件夹。除其他内容外，实验注册表存储算法、问题与作业定义；已提交、运行中与已完成作业的日志输出与状态；作业结果；以及「集群函数（cluster function）」，它以一种与调度软件无关的方式定义与调度系统的交互。

下面，我们在工作目录的子目录中创建一个注册表——在真实的集群上，请确保该文件夹存储在共享网络文件系统上，否则节点无法访问它。我们还将注册表的 seed 设置为 1，把 packages 设置为 "mlr3verse"，这将使这些包在我们所有的实验中可用。

library(batchtools)

# 创建注册表
reg = makeExperimentRegistry(
  file.dir = "./experiments",
  seed = 1,
  packages = "mlr3verse"
)

注册表创建完成后，我们需要用问题与算法来填充它以形成作业，这一步用 mlr3batchmark 最容易完成，不过用 batchtools 也可以实现更精细的控制，这将在11.2.4 节中探讨。batchmark() 把 mlr3 任务与重采样转换为 batchtools 问题，把 mlr3 学习器转换为 batchtools 算法；随后为所有重采样迭代创建作业。

batchmark()
library(mlr3batchmark)
batchmark(large_design, reg = reg)

11.2.2 作业提交（Job Submission）

定义了实验之后，我们现在可以把它们提交到集群。然而，最佳实践是先用 testJob() 单独测试每个算法。例如，我们只测试第一个作业（id = 1），并使用外部 R 会话（external = TRUE）。

testJob()
result = testJob(1, external = TRUE, reg = reg)

一旦我们确信作业定义正确（对于出错的作业见11.2.3 节），就可以继续提交它们，即为每个计算作业指定资源需求，然后（可选地）对作业进行分组。

资源的配置取决于注册表中设置的集群函数。我们将假设在一个 Slurm 集群上工作，并相应地用 makeClusterFunctionsSlurm() 初始化集群函数，同时使用 slurm-simple.tml 模板文件，该文件可以在 batchtools 包自身的子目录中找到（确切位置可通过运行 system.file("templates", package = "batchtools") 获得），也可以在 batchtools 的 GitHub 仓库中找到。模板文件（template file）是一个带占位符的 Shell 脚本，由 batchtools 填入内容，其中包含通过 Rscript 或 R CMD batch 启动计算的命令，以及作为调度器注释的注释行，例如用于传达资源或文件系统上的路径。

这个示例模板在许多 Slurm 安装上开箱即用，但你可能需要根据自己的集群进行修改——它可以被定制以适配更高级的配置。

cf = makeClusterFunctionsSlurm(template = "slurm-simple")

为了在本地机器上继续示例，我们建议用 makeClusterFunctionsSocket() 把集群函数设置为 Socket 后端。选定的集群函数可以通过传给 $cluster.functions 字段保存到注册表中。

reg$cluster.functions = cf
saveRegistry(reg = reg)

注册表设置好之后，我们现在可以决定是否要分块运行实验（10.1 节），然后为提交的作业指定资源需求。

对于这个例子，我们将使用 chunk() 对作业进行分块，使得一个重采样实验的五次迭代在一个计算作业中顺序运行——在实践中，最优分组高度依赖于你的实验（10.1 节）。

chunk()

chunks = data.table(
  job.id = ids, chunk = chunk(ids, chunk.size = 5, shuffle = FALSE)

最后一步是决定每个作业的资源需求。资源集合取决于你的集群与相应的模板文件。如果你不确定资源需求，可以用宽松的资源约束启动一部分作业，例如你的计算站点允许的最大运行时间。测得的运行时间与内存使用随后可用 getJobTable() 查询，并用于更好地估计剩余作业所需的资源。在本例中，我们将每个作业的 CPU 数设置为 1，墙钟时间（walltime，即调度器停止作业前的时间限制）设置为 1 小时（3600 秒），内存限制（调度器停止作业前的内存上限）设置为 8000 兆字节。

背景与解释（译者注）：把多个小的重采样迭代「打包」成一个集群作业（chunking）能显著降低调度开销——调度系统对每个作业都有排队与启动成本，作业数量越少、粒度越粗，吞吐越高；但代价是单个作业的运行时间变长、失败后重算的粒度变大。最优 chunk 大小取决于单次迭代耗时、队列限制与节点资源，实践中需要权衡。模板文件（template）是 batchtools 与调度系统之间的「翻译层」：它本质上是一段带占位符的 Shell 脚本，batchtools 会填入作业参数后交给调度系统执行。

resources = list(ncpus = 1, walltime = 3600, memory = 8000)

所有要素就绪后，我们现在可以提交作业了。

submitJobs(ids = chunks, resources = resources, reg = reg)

# 等待所有作业结束
waitForJobs(reg = reg)
提交作业（Submitting Jobs）

提交计算作业的一个好方法，是在头节点上使用一个持久的 R 会话（例如使用终端复用器 Terminal Multiplexer, TMUX）在后台持续提交作业（或进行计算，取决于集群函数）。

然而，batchtools 注册表保存在文件系统上，因此在 R 会话终止时仍然持久存在。这意味着你也可以从交互式 R 会话提交作业、终止会话，然后在新的会话中稍后分析结果。

11.2.4 用 batchtools 实现自定义实验（Custom Experiments with batchtools）

本节涵盖高级机器学习或技术细节。

一般来说，我们建议使用 mlr3batchmark 在 HPC 上调度较简单的 mlr3 作业，不过我们也会简要展示如何在不使用 mlr3batchmark 的情况下使用 batchtools，以便对你的实验进行更精细的控制。同样，我们首先创建实验注册表。

reg = makeExperimentRegistry(
  file.dir = "./experiments-custom",
  seed = 1,
  packages = "mlr3verse"
)

然后「问题（Problem）」用 addProblem() 手动注册。在这个例子中，我们将注册上面 large_design 的所有任务-重采样组合，以任务 ID 作为唯一名称。我们指定问题的 data（即学习器训练/测试的静态数据）为任务/重采样对。最后，我们传入一个函数（fun，动态问题部分），它接收静态问题的 data 并原样返回，作为问题的 instance 而不做任何改动（图 11.2）。下面显示的 fun 是默认行为，本可省略，我们为了清晰起见展示它。这个函数可以更复杂，并接受更多参数来动态修改问题实例。

for (i in seq_along(tasks)) {
  addProblem(
    name = tasks[[i]]$id,
    data = list(task = tasks[[i]], resampling = resamplings[[i]]),
    fun = function(data, job, ...) data,
    reg = reg
  )
}

接下来，我们需要用 addAlgorithm() 指定要运行的算法。算法同样用一个唯一的 name 指定，以及一个定义实验计算步骤并返回结果的函数。

在这里，我们定义一个作业来代表一个完整的重采样实验。一般来说，batchtools 中的算法可以返回任意对象——这些对象就存储在文件系统上，可以在收集结果时用自定义函数处理。

addAlgorithm(
  "run_learner",
  fun = function(instance, learner, job, ...) {
    resample(instance$task, learner, instance$resampling)
  },
  reg = reg
)

最后，我们将用 addExperiments() 定义具体的实验，传入问题设计（prob.designs）与算法设计（algo.designs），分别给问题与算法分配参数（图 11.2）。

在下面的代码中，我们为六个任务的所有重采样迭代添加实验。通过不指定 prob.designs，默认会为所有现有问题创建实验。我们把算法的 learner 参数（"run_learner"）设置为 large_design 对象中的三个学习器。注意每当添加一个实验时，当前种子会被分配给该实验，然后递增。

alg_des = list(run_learner = data.table(learner = learners))
addExperiments(algo.designs = alg_des, reg = reg)
summarizeExperiments()

我们的作业现在可以提交到集群了；通过不指定具体的作业 ID，所有实验都会被提交。

submitJobs(reg = reg)

11.3 统计分析（Statistical Analysis）

基准实验的最后一步是使用统计检验来确定哪个（如果有的话）学习器表现最好。mlr3benchmark 为对 BenchmarkResult 对象应用统计显著性检验提供了基础设施。

目前支持 Friedman 检验与两两配对 Friedman-Nemenyi 检验 (Demšar 2006)，用于分析至少包含两个独立任务与至少两个学习器的基准实验。作为第一步，我们建议用 $friedman_posthoc() 进行学习器之间的两两配对 Friedman-Nemenyi 检验。该方法首先执行一次全局比较，看是否有学习器在统计上优于另一个。要使用这些方法，我们首先用 as_benchmark_aggr() 把基准结果转换为 BenchmarkAggr 对象。

as_benchmark_aggr()

背景与解释（译者注）：当在多个数据集上比较多个算法时，不能简单地按「胜出数据集个数」或逐数据集做 t 检验下结论——这会引入多重比较问题与对「算法整体排名」缺乏形式化。Demšar（2006）提出的方案是：先对每个数据集上各算法的性能排序，再在「平均秩（mean rank）」上进行 Friedman 检验（全局是否至少有一对算法显著不同），若有显著性再作 Nemenyi 两两事后检验。与之对应的图是临界差异图（critical difference diagram）：图中一条水平线把「两两差异不显著」的算法连在一起，显著不同的算法之间不连线。需要注意的是，以平均秩为依据的检验对「差值大小」不敏感，只看排序，这是它与以原始性能值为输入的检验（如配对 t 检验）的一个关键区别。

library(mlr3benchmark)
bma = as_benchmark_aggr(bmr, measures = msr("classif.ce"))
bma$friedman_posthoc()

利用图 11.3，我们可以得出结论：平均而言随机森林的秩最低（即最好），其次是逻辑回归，然后是无特征基线。虽然随机森林在统计上优于基线（图 11.3中两者之间没有连线），但它在统计上并不优于逻辑回归（图 11.3中两者之间有连线）。我们现在还可以把它与 Couronné、Probst 与 Boulesteix (2018)开展的大型基准研究进行比较，在那项研究中随机森林在 243 个真实数据集的 69% 上优于逻辑回归。

11.4 结论（Conclusion）

在本章中，我们探讨了如何使用 mlr3 开展大规模机器学习实验。我们展示了如何通过 mlr3oml 接口包从 OpenML 获取多样化的数据集，如何通过 batchtools 与 mlr3batchmark 的集成执行大规模实验，以及最后如何用 mlr3benchmark 分析这些实验的结果。关于 batchtools 的进一步阅读，我们推荐 Lang, Bischl, and Surmann (2017) 与 Bischl et al. (2015)。

11.5 练习（Exercises）

在这些练习中，我们将开展一项实证研究，分析随机森林是否比单一决策树具有更强的预测能力。我们的零假设（null hypothesis）是两者性能没有显著差异。

  1. 加载 ID 为 269 的 OpenML 集合，它包含来自 AutoML 基准 (Gijsbers et al. 2022)的回归任务。浏览这个套件，研究其中包含的数据集及其特征。然后找出所有观测数少于 4000 的任务，并把它们转换为 mlr3 任务。
  2. 创建一个实验设计，在这些任务上比较 lrn("regr.ranger") 与 lrn("regr.rpart")。对两个学习器都使用 robustify 流水线，并使用无特征回退学习器。为节省时间，可以使用三折交叉验证来代替 OpenML 重采样。用 batchtools 运行比较实验。使用默认超参数设置，不做任何调优，以保持实验简单。
  3. 进行全局 Friedman 检验，并在适当情况下进行事后 Friedman-Nemenyi 检验，解释结果。使用 MSE 作为评估度量。
